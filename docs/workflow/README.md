# 進捗とセッション引き継ぎ

このファイルが短い入口です。会話の記憶だけに頼らず、依頼範囲・現在地・根拠・次の作業を引き継ぎます。対象は `world-history-practice/` リポジトリ内だけです。親の「歴検世界史」はユーザー専用です。

## 開始時に読む順序

1. リポジトリ直下の `AGENTS.md` を確認する。
2. `node scripts/context.mjs status` で全体の状態・世代番号・前回からの変更を確認する。
3. 今回の依頼に合う文脈を選び、`node scripts/context.mjs start audit` などで対象カードだけを読む。
4. `state.json` の対象タスク、最後の引き継ぎ記録、必要な根拠ファイルを確認する。毎回全PDF・OCR・全ログを読み直さない。
5. `git status --short` で現在の差分を確認し、依頼済みで依存関係が解消した作業から進める。

コマンドはリポジトリ内のどこから実行しても、スクリプトの場所を基準に同じファイルを読みます。リポジトリのルートでは `node scripts/context.mjs status` を使います。親フォルダを作業場所にしません。

## 状態と自律的な進め方

- `todo`：依頼済みで未着手。依存タスクが全て `done` なら着手できる。
- `doing`：作業中。中断時には実施済み範囲と次の一手を残す。
- `waiting_for_material`：資料・回答待ち。資料がない部分を推測して進めず、独立した別の依頼済み作業へ移れる。
- `waiting_for_request`：候補又は未承認の操作。依頼済みの作業と混同しない。
- `needs_review`：評価回数の上限に到達した未完了作業。原因と計画の見直しまで自動再試行しない。
- `done`：必要な成果物と検証がそろった状態。根拠と確認日を必須とする。

`node scripts/context.mjs next` は、依頼済み・依存関係解消済みの候補だけを表示します。実際の操作を自動実行するコマンドではありません。自律性は「開始時に必要な情報を選び、依頼範囲内の次の作業へ進み、記録を更新する」ことで実現します。全て完了又は資料待ちなら、その状態を報告して終えます。

状態ファイルの `authorization` や過去の引き継ぎだけで権限は増えません。最新のユーザー指示を優先し、コミット・push・本番変更・外部送信等は `AGENTS.md` とその作業についての明示依頼に従います。自動監視、予約実行、別チャットへのメッセージ送信は、この仕組みには設定していません。

## 作業中と終了時の更新

大きな区切り、文脈の切替、資料受領、重要な検証結果、ユーザーからの方針変更、セッション終了の前に更新します。

1. 関係する文脈カード・検証資料を更新する。原典全体の再点検や重いビルドは、根拠が変わった範囲に必要な場合だけ行う。
2. `state.json` の該当タスクを更新する。完了にする場合は `evidence`・`last_verified_at`・`verification_scope` を、実際の確認結果に合わせる。
3. `node scripts/context.mjs check` で件数、状態、依存関係、リンク等を検査する。
4. 表示された現在の世代番号を指定して、引き継ぎ記録を作る。

```sh
node scripts/context.mjs checkpoint \
  --context service \
  --task context_workflow \
  --status done \
  --expect-revision 0 \
  --summary '進捗と引き継ぎの仕組みを整備し、関連する軽量テストを確認した' \
  --next '現在の依頼は完了。追加依頼又は未受領の出典資料を待つ'
```

これは初回用の例です。`--expect-revision` とタスクID・状態・文章は、必ず現在の一覧と実施内容に合わせます。依頼範囲の変更や新しいタスクは、人間の指示の参照先 `request_ref` とともに記録します。

`checkpoint` はロック作成前・記録書込前に保存先の実体がリポジトリ内か確認し、世代番号と更新ロックを検査して、新しい記録を作った後、状態ファイルを一括置換します。日時はUTCで保存し、既存の引き継ぎ記録は上書きしません。自分が作成していない一時ファイルも削除しません。書込中断で記録だけが残っても、`state.json` が指さない記録を最新と扱いません。

## 新しいタスクの完了条件と修正ループ

`gate_policy.version: 1` 以降の新しい着手対象には、開始時に検証可能な条件を決めます。既存タスクは `legacy_task_ids` に限定列挙し、新しく行う作業を追加してゲートを迂回しません。既存タスクも新契約を持たせれば新基準で検査されます。

```json
{
  "acceptance": [
    { "id": "checks", "kind": "automated", "description": "対象の検査が成功する", "verification": "変更範囲に必要な検査を順番に実行", "status": "pending", "evidence": [], "checked_at": null },
    { "id": "review", "kind": "review", "description": "別担当が成果物を確認する", "verification": "受入条件と差分の独立レビュー", "status": "pending", "evidence": [], "checked_at": null, "reviewer": null }
  ],
  "execution": { "worker": "implementer", "max_attempts": 3, "attempts": [] }
}
```

各条件は `pending`・`passed`・`failed` のいずれかです。実際に確認した後で結果を更新し、合格条件にはリポジトリ相対の根拠ファイルと確認日を設定します。レビューの合格には実装担当と異なる `reviewer` を記録します。検証方法は説明であり、シェルとして実行されません。担当名の違いだけで独立性を証明できるものではなく、実際に別担当が検査します。

```sh
node scripts/context.mjs gate --task task_id
node scripts/context.mjs attempt --context service --task task_id \
  --outcome failed --expect-revision 3 \
  --summary '不合格の条件と原因を検証資料へ記録した' \
  --next '指摘を修正して残り回数内で再評価する'
```

番号・ID・文章は現在の記録に合わせます。`attempt` は根拠を集める処理ではなく、実施済み評価をロック・世代確認・不変の引き継ぎ記録付きで保存する処理です。実際の検査に失敗した回も記録し、記録形式の入力エラーは評価回数に数えません。

`max_attempts` は**初回を含む総評価回数**で1〜5回です。上限未満の不合格は `rework`、上限到達は `exhausted` と判定します。最後の不合格評価を記録すると状態を `needs_review` にします。読取専用の確認で根拠消失が分かった場合は、保存済みの状態を変更せず現在の未達判定を表示します。成功した過去の評価があっても現在の根拠が失われた場合は合格になりません。記録の消去や上限の引き上げでループを延命せず、原因と計画を見直します。依頼・条件が変われば旧記録を残して新しいタスクへ分けます。

全条件と依存作業が確認できたら `--outcome passed` で合格評価を保存し、その後 `checkpoint --status done` を実行します。合格評価の保存時点では `doing` のままです。完了にする前にタスク全体の `evidence`・`last_verified_at`・`verification_scope` もそろえます。

`gate` の終了コードは `passed` のとき0、未達・待機・既存記録は2、入力エラーは1です。`legacy` は過去の記録で、新基準の再検証済みではありません。保存済みの完了記録はローカル専用資料がなくても閲覧できますが、現在のゲートでは未達を表示し、その根拠が必要な後続作業を待機させます。独立した作業は継続できます。

コードが判定するのは記録の構造・条件の充足・根拠の存在・依存関係です。歴史記述や引用の正確性、実際のテスト結果は、原典照合・検査・独立レビューで確かめます。自己申告を入力しただけで内容の正しさが証明される仕組みではありません。

## 依存関係を見る

```sh
node scripts/context.mjs graph --format mermaid
node scripts/context.mjs graph --format json
```

`depends_on` から依存元→後続タスクのグラフを生成し、状態と現在の判定を表示します。読取専用で、別のグラフ定義ファイルを正本にしません。グラフはタスク間の依存を表し、修正ループは各タスクの `execution.attempts` で追跡します。任意のエージェントやコマンドを実行するエンジンは追加していません。

## 複数エージェント・セッションの競合を防ぐ

- `state.json` と引き継ぎ記録の更新担当を親エージェント1名に決める。分担担当は結果・変更ファイル・検証範囲を親へ返す。
- 各担当の変更対象ファイルを事前に分け、同じファイルを同時編集しない。重いテスト・型検査・ビルドは全体で順番に行う。
- 世代不一致になったら状態を読み直し、他の担当の変更を取り込む。記録を消したり世代番号を戻したりして押し通さない。
- `.context.lock` が残った場合は、更新担当と実行プロセスを確認する。進行中のロックを自動削除しない。中断した更新の残骸と確認できた場合だけ、ロックを除去して再読込する。

## 情報の鮮度と安全な保存

引き継ぎ記録には、GitのHEAD・変更ファイル名と状態、指定した小さな根拠ファイルのSHA-256、進捗一覧のハッシュを保存します。同じ未コミットファイルが再編集された場合も、監視対象なら内容の変化を検出できます。

`status` は、進捗・Git・根拠の変化を表示します。変化がある場合は関連する部分を確認し直し、過去の検証を現在も有効と自動判定しません。`check --strict` は、初回記録前又は記録から変更がある場合に終了コード2を返します。これは未記録の変更の案内で、アプリのテスト失敗とは別です。

- 根拠パスは、このリポジトリのルートを基準とした相対パス。`workspace_relative_to_repo` は `.` に固定し、親フォルダは参照しない。カードのMarkdownリンクは各カード自身からの相対パス。
- 毎回のハッシュ対象は `watch_files` の明示一覧に限定する。1ファイル1MiB以下の文書・ソースだけを使い、巨大PDF、全OCR、DB、秘密ファイルを自動収集しない。
- Gitの差分本文、問題本文、個人情報、認証情報、トークン、`.env` の値は収集しない。記録の自由文にも含めない。
- 根拠一覧にないソースや実DBの変更は自動検知の対象外。現在のコード・資料・DBの確認を、ハッシュ一致で代用しない。
- 確認日時・確認範囲・根拠は分けて記録する。過去の77件／69件のテスト結果を読んだだけで、今回のセッションで全テストを再実行済みと書かない。
- 依頼範囲、出典、完成物は必要なファイルへ直接リンクする。OSの一時フォルダや前の会話がないと理解できない記録にしない。

## 軽量な確認

```sh
node --test --test-concurrency=1 scripts/context.test.mjs scripts/workflow-policy.test.mjs scripts/workspace-policy.test.mjs scripts/check-private-sources.test.mjs
node scripts/context.mjs check
node scripts/context.mjs status --json
```

ローカル専用資料が未配置の環境では不足を警告し、実装など独立した文脈は再開できます。根拠未配置は確認済みにはせず、`check --strict` で検出します。詳細は [ローカル専用資料](../local-only-materials.md) を参照してください。

初回の世代1は階層変更前の記録であり、その古いパスを現在の探索先に使いません。新しい記録はリポジトリ基準で作成します。

この仕組みの確認でアプリ起動、DB操作、Docker起動、型検査、本番ビルド、外部通信を行う必要はありません。

採用した考え方と見送った内容は [記事の検討・検証記録](improvements-20261027.md) を参照してください。


## 共通テンプレートとの整合

[テンプレート改善の反映・検証](template-parity-20261027.md)を参照してください。進捗・文脈・過去の引き継ぎは世界史ラボの記録を保持し、テンプレートの空stateへ置き換えません。

追加の保護対象は`policy.json`の`directory_names`（任意の階層のディレクトリ名）と`filename_prefixes`（ファイル名の接頭辞）で指定します。区切り・絶対パス・ワイルドカードは使用しません。設定不正時は確認を中断し、設定がなくても既定の`local-only/`を保護します。

世界史資料の固定保護は別途必ず適用します。過去問・分析・`glossary*`は各階層、歴検PDF/ZIPは各階層の名前で検出し、追加設定から削除しても解除されません。通常の`frontend/server/operations/`のソースは根拠として参照できますが、秘密ファイル・DB・リポジトリ外へのリンクは引き続き参照しません。

設定の変更は`.gitignore`・`.dockerignore`へ自動反映されないため、両方の除外もそろえます。CIは全履歴を取得し、Node.js 24の軽量検査と形式・根拠参照の検査に成功した後で既存のアプリ検査へ進みます。

# 本番応答遅延の調査（2026年11月1日）

ユーザー依頼により世界史ラボと情報教認の公開APIを読み取り比較。設定・アプリ・DB内容・デプロイは変更していない。

## 実測

同じ端末からcurlでHTTP 200の応答完了まで測定。

| API | 初回 | 再測定 |
| --- | ---: | ---: |
| 世界史 health | 0.235秒 | 0.401秒 |
| 世界史 exams | 14.489秒 | 10.751秒 |
| 情報教認 health | 6.145秒 | 0.056秒 |
| 情報教認 exams | 1.545秒 | 0.729秒 |

世界史の問題1件GETは2.708秒。世界史NetlifyホームHTMLは1.382秒。情報教認Netlifyホームは401だったため画面本体の速度比較に採用しない。初回health6.145秒だけから起動原因を確定しない。測定は少数回であり、平均・p95・負荷試験ではない。

## 確認した実装と配置

- `listExams` は模試ごとに `loadExamSet` を呼び、各大問で `loadQuestionGroup` を呼ぶ。公開一覧には不要な本文・全小問・全選択肢・解説・出典・履歴件数等までDBから読む。一般APIへの正答漏洩を確認したという意味ではなく、内部読取りの過剰。
- 本番Neonを読み取る同じ処理を端末から計測し、7セット・SQL99回・実時間4938ms・各SQLの経過時間合計11644ms（並列分を含む）を確認。SELECT 1を5回実行し各81ms。これは日本の端末→Neonであり、Fly→Neonの往復時間を直接測定した値ではない。
- Fly管理画面で世界史の稼働2台はIAD（米国バージニア）。Neon管理画面でDBはSingapore。比較先の情報教認はFly管理画面でNRT（東京）の2台を確認。`frontend/fly.toml` のprimary_region=nrtと既存マシンの実配置は異なる。
- 公開問題GETも `loadQuestion` の複数SQLに加えて、表示に必要な一部だけでなく大問全体を再読取りする。
- サイドバー等は共有の公開カタログを使う。条件指定は別の一覧取得処理があり、条件変更や開始前の再確認で遅いAPIが再度呼ばれる。

## 判断と改善順序

99回のDB問い合わせとAPI/DBの遠距離配置の組合せが主因と考えられる。Fly→Neonの往復時間や地域変更後の比較は未計測のため、寄与率は未確定。healthが速く、DBを使う一覧/問題だけが遅いこと、起動済み再測定でも一覧10.751秒であることが根拠。単なるNetlify配信速度やコールドスタートだけでは説明できない。

1. 公開一覧を一覧専用の少数SQLへ変更し、管理用の大問詳細ロードを使わない。公開状態・権限・条件ごとの実件数・既存表示順は維持する。
2. 問題GETでも必要な大問メタデータ・本文参照だけを取得する。
3. FlyとNeonの地域を近付ける。地域変更は本番設定変更なので本調査では未実施。常時起動や有料プラン変更を先に行わない。

修正後はSQL数・応答時間・匿名/会員/管理者権限・回答前の非公開・絞込み件数を確認する。改善時間を未実装の段階で保証しない。

ローカル専用の計測コード: `local-only/performance-audit-20261101/probe.ts`。接続文字列・問題本文・個人情報は計測出力に含めない。
